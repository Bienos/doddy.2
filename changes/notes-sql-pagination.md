`GET /v1/web/memory/notes` now reads one page of encrypted rows from the database (`LIMIT/OFFSET`, same order `captured_at DESC NULLS LAST, note_id`, same user filter) plus a separate `count(*)`, instead of loading every row and slicing in memory. Request, response shape (`notes`, `total`, `nextOffset`, `unreadable`), offset semantics, decryption of the page only, and per-account isolation are unchanged; a row that no longer decrypts still counts in `total`. The web client and the iPhone use the same endpoint and need no change (the iPhone only PUTs the whole list). Search is untouched.
Measured on pglite in-process with 5,000 synthetic notes (not production; includes the local HTTP round trip): a 100-note page fetched 5,000 note rows in about 94 ms (median of 5) before and 100 rows in about 7 ms after; at offset 4,900, 5,000 rows and 103 ms before, 100 rows and 8 ms after. Search over all 5,000 notes (unchanged) fetches 5,000 rows and takes about 136-142 ms median here. Reproduce with `DODDY_BENCH=1 node --test dist/test/memory-notes-pagination.test.js` after `npm run build`. A search index or vector database is not justified without production data: search is lexical, per-person rate limited, capped at 5,000 notes, and an index over decrypted text would put note content outside the encrypted column; revisit only if real traffic shows search latency or load.
No index added: the schema is created by `CREATE ... IF NOT EXISTS` on boot in `backend/src/store.ts` (there is no separate migration runner), so any new index would apply to production on the next start. The page query filters on the primary key prefix `(user_id, ...)` and sorts at most 5,000 rows; that was fast enough above. If production data ever needs it, a prepared, not-applied option is `CREATE INDEX memory_notes_user_captured ON memory_notes (user_id, captured_at DESC NULLS LAST, note_id);`.
