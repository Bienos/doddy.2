Backend: the backend's half of "one token per server" (items 1 to 3 of `docs/decisions/2026-11-12-one-token-per-server.md`). New `POST /v1/session/account` takes the Doddy account's Supabase token once, plus the iPhone's device id, and answers a `ds1` session for that account on that iPhone (`{ token, expiresAt, access, deviceListId }`): signed as every `ds1` token is, 30 days long, naming the iPhone's stored row (`dev`) and saying it is an account session (`acc`). It is the same account as its Supabase token on every route (same cut-off, same data an account took over from an iPhone), it is listed in `GET /v1/web/devices`, and it ends at once on a revoke (`DELETE /v1/web/devices/:id`, which the iPhone's own session can call: that is the sign-out) and on account deletion. Everyday routes accept both the Supabase token and the session; nothing stops accepting the Supabase token. Decision `2026-11-14-backend-account-session`; endpoints in `docs/platforms/web.md`.
- **A revoked iPhone and the device-session rule.** The device-session path (`POST /v1/session/device`) still refuses a revoked iPhone and no route clears it; account sessions use separate rows (one per account and iPhone, `devices.account_id`) that the device-session path never reads. For an account-session row the way back is the exchange with a fresh Supabase token of the same account: it gives the row a new id, so nothing made before the revoke comes back. A revoke does not end the account's Supabase session (Supabase's).
- **Limits** with the numbers the other sign-in routes use, no new setting: 20 tries per address per hour (counted before the token is looked at), 20 exchanges per account per hour (429 with `Retry-After`), 20 iPhones per account that are not revoked (a new one beyond that gets 429 `quota_exceeded`; revoked ones take no place).
