iPhone: once the backend takes the Doddy account, the app asks it for a session of its own (`POST /v1/session/account`, merged as #486) and sends that session to the backend instead of the account's Supabase token. The session (a `ds1.` token of 30 days, its `expiresAt`, its stored iPhone's `deviceListId`, and the account and server it belongs to) is one Keychain item, apart from the iPhone's earlier device session. With none, one the backend refused (401) or one within two days of its end, the app exchanges a fresh Supabase token; when no session can be had (a server without the route, which production answers until it has a session key; one not set up for it; a 429; offline; an answer that isn't an account session for this account) the Supabase token is sent exactly as before and nothing is written down about it (in one launch a failed exchange is not asked again for five minutes, an hour after a 429). A 429 at an everyday request passes through as it always did. The link no longer picks "whatever starts with `ds1.`": the earlier device session is taken only when its claims don't say `acc` and it isn't the account session the app holds, and `linkBackend` and `undoBackendLink` refuse an account session themselves, so it never reaches the link routes. Signing out, deleting the account and another account taking the iPhone over forget the session at once and keep the backend's end (`DELETE /v1/web/devices/:id`, made with the session itself) owed in a second Keychain item until the backend confirms it (a 200 with `revoked: true`, or a 401); tried now, at each launch and at each sign-in; nothing is called ended unless the backend said so (DOD-08, DOD-11). Both items are in `DeviceKeychain` and `docs/architecture/DEVICE_DATA_STORES.md`. Decision `2026-11-12-one-token-per-server` (backend, app half; server half `2026-11-14-backend-account-session`).
