# A call for you starts from one field, "who and why"; a model proposes the brief, code checks it, the card is unchanged

- **Date:** 2026-11-13
- **Decided by:** owner, 12–13 Nov 2026: the review's proposal for "Doddy dzwoni w moim imieniu" ("jedno pole „Do kogo i po co”, resztę uzupełnia Doddy; pokazuje kartę do zatwierdzenia z dokładną treścią", `docs/strategy/PRZEGLAD_APLIKACJI_2026-11-12.md`, section 4), then "Wszystko dawaj" after the review.
- **Status:** applied in the pull request that adds this file. The server part is tested with a fake model against Postgres; the iPhone screens are **not compiled** (no Xcode here) and not run on a device. Nothing reaches users until `doddy-messaging` is deployed and the app is built.
- **Replaces:** the first screen of a new call in Calls for you (the full brief editor, ADR-501). The editor, the card (ADR-500) and the approval bound to the card's digest are unchanged. Follows "Not in this change: the brief editor" in `2026-11-12-phone-calls-hub.md`.

## Why
A new call was about four screens and eight or more fields: who, the number, where it came from, on whose behalf and its genitive, the goal, the question, facts with kinds, the length. Most people know only "call the hairdresser on Długa and ask about Saturday". The constitution's rule (DOD-07: the approval is bound to the exact payload, and a changed payload voids it) is about the card, not about how the brief is typed, so the typing can be shorter as long as the card stays exact.

## Decision
1. **One field first.** New call opens a screen with one field, "Who and why" (8 to 400 characters), the contact pick as an option, Next, and "Fill in every field myself", which opens the full editor exactly as before.
2. **The model only proposes.** Next sends the words, and the picked contact's name (never its number), to `POST /v1/call-cases/draft` on the messaging server. The server asks Claude (`ClaudeBriefDrafter`, `claude-opus-5-5` at low effort, structured output in a closed schema: `callee_name`, `goal`, `question`, `facts[{kind, text}]`). The schema has no number field.
3. **Typed code decides** (`server/messaging/src/taskCalls/draft.ts`, `checkDraft`), field by field. A field that fails is dropped with a reason code and reported as missing; nothing is repaired or guessed:
   - **The number** is read from the user's own words by code (`readNumbers`): exactly one number Doddy may call (the same allowlist as a call, `phone.ts`; not the user's own number, not Doddy's). Two or more, or one Doddy may not call, leave it for the user. The app uses the picked contact's number instead when there is one, and uses the server's only if its digits are in what the user wrote.
   - **The name** must be made of words the user wrote (Polish endings allowed: "Fryzjer Anna" from "do fryzjera Anna"); the picked contact's name counts.
   - **The question** must end with "?", must not commit Doddy (`commits`, the same check as the brief), and like every field must hold no number, hour or date the user didn't write.
   - **Facts** must be copied from the words; at most five; an address becomes a fact marked Address, which the app leaves unticked (only ticked facts leave the iPhone, as before).
   - Every field passes the brief's own content rules (no braces, no PESEL, card or account number, no address outside a fact) and its length limits.
4. **Words that hold a PESEL, a card number or a bank account number are refused before the model sees them** (400 `brief_refused`, field `text`); the screen says to add a PESEL on the next screen as a fact, if Doddy really needs it.
5. **The editor opens filled in for review**, with a note on top ("Doddy filled this in from what you wrote. Check every field…") and one line per field Doddy left out. Who (name, number) and the goal and question are open; on whose behalf, where the number came from, the facts, what Doddy must not do and the length are folded under one **Details** row with a one-line summary. Details open by themselves when one of them needs fixing (no first name, too many or wrongly marked facts). "Change the brief" on a card opens the editor with Details open, as before.
6. **The card is unchanged.** "Prepare the card" sends the brief to `POST /v1/call-cases` as before; the server compiles the exact payload and the card shows who, the number, the opening line word for word, the question, what Doddy may say and must not do; nothing is dialled until the user approves that card's digest.
7. **Anything else falls back to typing.** No server, an older server (404), the model off (`drafter_not_configured`), a failed model call (502 `draft_failed`), a rate limit or no connection: the editor opens with the user's own words as the goal (if they fit) and the picked contact, and a note that Doddy couldn't fill it in. A call never depends on the model.
8. **Limits and cost.** The endpoint needs a device token, task calls configured and not switched off, and a verified phone number (the same as making a call), so nobody without a way to call spends the model. 20 drafts per device per hour, like the neighbouring routes. One model call per draft; no retries beyond the SDK's one.
9. **Privacy (DOD-11).** What goes to Anthropic: the user's sentence with every phone number replaced by `[numer]`, and the picked contact's name. Not the number, not the user's name, not facts from elsewhere, not memory. The server stores nothing from a draft (no table, no row) and logs only codes and counts (`missing`, `dropped` as `field:reason`, the number of facts, a drafter error code), never the words. The first screen says the words go to Claude (Anthropic) with the numbers taken out and that Doddy's server doesn't keep them; it doesn't claim anything about Anthropic's own retention.

## Consequences
- A typical call is: one sentence → Next → check → Prepare the card → approve. The fields are still all there, one tap away.
- Drafts cost a model call each (Claude Opus 5.5 at low effort; the answer card uses Claude Haiku 5.5). The owner may prefer Haiku 5.5 here too: it is one constructor argument (`new ClaudeBriefDrafter(key, { model })`); no env variable was added.
- The name check is strict on purpose: a model that writes "Salon fryzjerski Anna" for "fryzjer Anna" gets the name dropped and the user types it. If that proves annoying in use, loosen the rule in code, not in the prompt.
- No server-side model fallback on a refusal: a refusal is a 502 and the user types the fields.
- Not in this change: drafting a call that books (the editor's brief is ask-only; booking stays with `call_places` and its own card), several places from one sentence (that is `call_places` in a conversation), and the hub's other cards. `server/messaging/README.md` is not edited here because two open pull requests hold it; this file and `docs/implementation/CALL_CASES_STATUS.md` describe the endpoint.
