# Doddy Beta runs on its own staging services, databases, voice agents and capped keys

- **Date:** 2026-11-12
- **Decided by:** proposal, owner approval pending
- **Status:** proposed — waiting for the owner. Nothing is created, deployed or changed by this file.
- **Replaces:** nothing. Carries out the server half of ADR-812 (`com.bienos.doddy2.dev` is Doddy Beta; production gets its own bundle id). The app half was left there for a later pull request.

## Why
- **Testers' builds should talk to their own servers.** Trying a change with Doddy Beta should never touch the data, voice agents or spend of the App Store app. The server addresses the app uses live in `Config/Doddy-Info.plist` (`DoddyServerURL`, `DoddyAccountsURL`, `DoddyAccountsPublishableKey`), `ServerConfig.defaultBaseURL` (`DoddyApp/Infrastructure/Server/ServerConfig.swift`) and `VoiceConfig.tokenEndpointAddress` (`DoddyApp/Features/Voice/VoiceConfig.swift`). Those are where a per-build choice goes.
- **ADR-812 already decided the app side** (`DECISIONS.md`): Doddy Beta keeps `com.bienos.doddy2.dev`, its App Store Connect record, its APNs setup and its App Group. Production gets a new App ID and record (owner queue 21). A Beta build configuration, two schemes, per-configuration server addresses and the `doddy-beta://` scheme "come in a later pull request".
- **Each server should accept only its own app's bundle id**, so a Beta build and an App Store build can never be mixed up on a server.
- **Every agent id should be set explicitly per environment.** A staging voice server must set `ELEVENLABS_TRANSLATOR_AGENT_ID` as well as `ELEVENLABS_AGENT_ID` (`server/voice-token/README.md`, `server/voice-token/src/handler.js`).

## Decision (proposed)
Doddy Beta (TestFlight and Debug builds) talks only to staging. The App Store app talks only to production. Staging starts empty: no production data is copied.

### What the owner creates (consoles are the owner's, `AGENTS.md`)
1. **Apple:** nothing new for Beta (ADR-812 keeps its App ID, push and App Group). Production's new App ID and App Store Connect record (owner queue 21) are needed before production can be split off.
2. **Supabase:** a new project for Beta accounts, with Apple, Google and email sign-in set up the same way as the accounts project (owner queue 23, 25 and 28 describe those steps). Its redirect list has `doddy-beta://auth-callback` and the staging web origin. Its Postgres can hold the staging backend's database, or the backend gets a Render Postgres.
3. **Render:**
   - `doddy-staging`: the backend and Doddy Web, from `main`, auto-deploy on.
   - `doddy-messaging-staging`: the messaging server, with its worker (`RUN_WORKER_IN_WEB=1`, or a separate worker as in `render.yaml`).
   - `doddy-messaging-staging-db`: a Postgres on a paid plan, so it doesn't expire (owner queue 1).
4. **Vercel:** a project `doddy-voice-token-staging` (root directory `server/voice-token`) with its own Upstash Redis store.
5. **ElevenLabs:**
   - Staging copies of the five agents (main, translator, phone, task-call ask, task-call book), made from `voice-agent/` with `scripts/voice_agent_spec.py`, `server/messaging/scripts/setup-phone-agent.mjs` and `setup-task-call-agent.mjs --agent book`, authentication on. Their phone and task tools point at the staging messaging server (`PUBLIC_BASE_URL`).
   - Preferably a separate workspace: the post-call webhook is set per workspace (`server/messaging/README.md`), so a workspace of its own gives staging its own webhook.
   - A staging API key, with a credit limit if the plan offers one.
6. **Twilio:** a subaccount for staging with its own number and Verify service, geo permissions limited to the allowed countries, and usage triggers (the same settings as owner queue 12).
7. **Keys with caps, one per service, never shared with production:**
   - Anthropic: its own key with a monthly limit.
   - OpenAI: only if the news writer is on in staging; its own project with a budget.
   - Monid: a small separate balance.
   - Serper: only if errands are on.
   - Composio: its own project and auth configs, and a Google OAuth client for staging.
   - Duffel test key and Uber sandbox: only if those features are on.
   - Spend limits are set in each console (as in owner queue 2 and 13).
8. **Settings on the staging services**, from 1Password (ADR-493), never in the repository:
   - **Backend:** the `doddy` list in `render.yaml`. `DODDY_MODE=live`, `DODDY_ENV=production` and `DODDY_AUTH_MODE=supabase`, once the per-purpose keys of `2026-11-12-account-and-device-tokens` are in. `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are the staging project's, `DODDY_APP_RETURN_URL` uses `doddy-beta://`, and `DODDY_WEB_ORIGIN` is the staging address.
   - **Messaging:** its list in `render.yaml` and `server/messaging/.env.example`, with the staging Twilio, ElevenLabs and agent ids, and `APNS_BUNDLE_ID=com.bienos.doddy2.dev`.
   - **Voice server:** the table in `server/voice-token/README.md`, with `APPLE_BUNDLE_ID=com.bienos.doddy2.dev`, the staging `SUPABASE_URL`, both agent ids (main and translator), and its own `DODDY_SESSION_SIGNING_KEY`.

### What the repository then needs (one pull request each)
1. **App:** the Beta build configuration and scheme from ADR-812. The five addresses above become build settings per configuration, read from Info.plist. The URL scheme is `doddy-beta://` for Beta. Debug builds use staging.
2. **Servers:** a second Render blueprint (or a staging section in `render.yaml`). Staging targets in `secrets/manifest.json`, which already names a development vault. The voice server requires both agent ids to be set, and answers `server_not_configured` without them.
3. **Voice agents:** per-environment agent ids for `scripts/voice_agent_spec.py`, so a change is tried on staging before the owner applies it to production.
4. **CI:** an Xcode Cloud workflow for the Beta configuration into the Beta record; production builds stay as the owner sets them up after owner queue 21.
5. **Docs:** `STATUS.md` gets a staging column; `BUILD_AND_TEST.md` says which build talks to which servers.

## What the owner decides
1. Yes or no to staging for Doddy Beta, and whether Debug builds use it too (proposed).
2. A separate ElevenLabs workspace (proposed) or staging agents in the production workspace.
3. Render plans for staging (the free plan sleeps; the messaging database needs a paid plan to last), and Supabase's plan for the new project.
4. The spend limit for each staging key.
5. The order: staging first and production's split after owner queue 21, or both together.

## Consequences
- Testers' and agents' tries stay on staging data, staging voice agents and staging spend. A voice-agent change can be tried on staging first.
- Every console change is made twice, and two sets of keys and agents have to be kept in step: more work for the owner, and more cost (a second paid database, a second Twilio number, possibly a second ElevenLabs workspace).
- Staging accounts are separate: a tester has one account on Beta and another on the App Store app.
- With Beta on staging, production can take the new production bundle id (owner queue 21) without affecting testers.
