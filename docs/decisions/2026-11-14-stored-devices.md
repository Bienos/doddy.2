# The backend stores the iPhones it signs in, lists them, revokes them, and lets joins end

- **Date:** 2026-11-14
- **Decided by:** owner, "yes, as recommended" to `2026-11-12-account-and-device-tokens` (the 90 days included); this file records how part (c) and step 3 of (e) were built
- **Status:** applied in the pull request that adds it. Backend only. `doddy` has auto-deploy off, so nothing is live until the owner deploys; no setting has to change for it
- **Replaces:** nothing. Builds on ADR-563 (device sign-in), ADR-709 (token cut-offs), ADR-819 (an iPhone using another account), `2026-11-14-backend-keys-per-purpose`

## What is kept
One row per iPhone that signs in with its device id (`POST /v1/session/device`), table `devices`: a random row id, the iPhone's own user id, first seen, last seen, and when it was revoked. No token, no hash of one, no content. A second table, `device_cutoffs` (one number per account, below), and two columns on `device_joins`: the linked sign-in a join was made with (`identity_id`) and when it was last made (`renewed_at`).

The account an iPhone uses is not copied into its row. It is the iPhone's join while that join is on, else the iPhone's own user id, so each fact has one place and cannot disagree with itself. The list is "the iPhones that use this account now".

## Rules
1. **A token names its iPhone.** A device token made for a stored iPhone carries that row's id in one more signed claim, `dev`. The signing key, the key id, the signature format and every token made without the claim are unchanged. This is the only way for a revoke to end one iPhone's tokens and no one else's: before it a token carried only the account, and every iPhone on an account holds a token for the same account.
2. **Revoke.** `DELETE /v1/web/devices/:id`, by the iPhone's own session or a browser signed in to the account. The iPhone's next request is refused, the account's other iPhones are not touched (`RevocableSessionVerifier` asks `DeviceRegistry.allows`, the per-iPhone case next to the person-wide cut-off). The answer is made from what the store read back after the write, and a store that fails answers an error, never "revoked" (DOD-08). A repeat answers the first moment. An unknown id and another account's are the same 404 (cross-user isolation). A token that names a row the database no longer has is refused too, so a restored or replaced database does not vouch for old tokens; those iPhones sign in again by themselves and get a new row.
3. **A revoked iPhone stays revoked on the device-session path.** `POST /v1/session/device` refuses it, with a plain message, however often it asks; the sign-in's own write refuses it too, so a revoke that lands between the check and the write still holds. No route clears a revoke. An iPhone gets Doddy back by signing in on it with the account's own Apple or Google, which is a token that names no iPhone, so nothing here stands in its way. What is not allowed is the quiet way back: the app's automatic renewal with the device id.
4. **A join ends after `DODDY_DEVICE_JOIN_DAYS` (90) unless the iPhone signs in again with the same Apple or Google.** That sign-in is the existing join route (`POST /v1/web/oauth/join`); it renews the join and keeps the moment it was first made. The account's token of an iPhone whose join has ended is refused on the next request, like a revoke. The iPhone's next device sign-in is its own account's, as after Leave (ADR-819); signing in with the same Apple or Google joins again, while that sign-in is still linked to the account. The iPhone's own-account tokens are not affected by a join.
5. **Unlinking a sign-in ends every join made with it** (`Store.unlinkWebIdentity`, one transaction). Joins made before the sign-in was recorded have none, so they end with a sign-in of the same kind (Google or Apple): an unlink can end a little more than it needs to and never less.
6. **Tokens made before this change** name no iPhone, so they can't be tied to one. They keep working (nobody is signed out at deploy) and are ended by `device_cutoffs`: a revoke, and an unlink that ended joins, write the second before which the account's tokens that name no iPhone no longer work. The other iPhones on that account sign in again by themselves and get a token that names them. This only matters for the 30 days after the first deploy, when the last such token expires; the code can be removed then.
7. **Last seen** is written when an iPhone signs in and then at most once an hour (`DEVICE_SEEN_EVERY_MS`), not on every request. A note that fails to write never fails the request, and is logged, rarely, without an id.

8. **Undoing an account link** (`undoAccountLink`, `npm run account:unlink`) already ended the joins made since the link; the registry now drops what it remembered when the undo route does it, so those iPhones' tokens that name them stop on the next request (the operator command is another process, so there the server's 30 seconds of memory applies). It writes no cut-off for tokens that name no iPhone: that would also cut the iPhone's own earlier token, which the undo is giving back. Such a token expires on its own within 30 days of the first deploy.

## Existing iPhones, at the first start of the new version
- Every iPhone that has already joined an account gets its row, with first and last seen set to that moment, and every earlier join's 90 days count from that moment, whatever date it was made (`renewed_at` is set where it is empty). Later starts find nothing to do.
- Every other iPhone, the owner's and guests included, gets its row at its next sign-in. Its current token keeps working until it expires, and the app renews it two days before that, so the owner's iPhone is listed within 28 days.
- Nobody is signed out: tokens without `dev` are accepted as before, and a join made before this change is valid for 90 days from the first start.

## What the person sees (from reading the app, not from a device)
- **After a revoke**: the iPhone's next request to the backend is refused with 401; the app asks for a new session with its device id (`DeviceSession.renew`), is refused with the plain message, and `DeviceSessionClient.signIn` turns any refusal into "no session". The iPhone then shows what it shows when the server won't take it: the backend features say they are not set up. It works again after the person signs in on it with Apple or Google.
- **After a join ends**: the same 401 for the account's token, then the silent renewal succeeds with the iPhone's own account (a guest: Ask Doddy only). Settings › Doddy on the web shows no joined account and offers Sign in with Google or Apple again. The app does not renew a join by itself, so a joined iPhone is back on its own account after 90 days unless the person signs in again. The date is in `POST /v1/web/device-account` (`expiresAt`), for a later screen.

## Not covered
- iPhones that use the backend with the Doddy account's own token (Apple or Google, `LinkedAccountVerifier`) are not in the list: that token names no iPhone. They are listed once the backend issues its own per-iPhone sessions (`2026-11-12-one-token-per-server`). Signing the account out of such an iPhone is still Supabase's.
- The screens: the iPhone's Settings and the web's Settings › Sign-in methods are later pull requests.
- The messaging server's device tokens (part d) are not touched.

## Rollback
The tables and columns are additive and the earlier code ignores them. What the earlier code does after a rollback: it doesn't know `dev`, so it accepts tokens that carry it and a revoked iPhone's tokens work again; it signs a revoked iPhone in again; joins don't expire; an unlink doesn't end joins; an account deleted while it runs leaves that iPhone's row and cut-off behind (ids and times only; the cut-off is dropped after 31 days, an iPhone row 180 days after it was last seen). Revokes already made are kept in `devices` and apply again when this version runs again, and joins made meanwhile get their 90 days from that next start. Roll back only for as long as a revoke isn't needed.
