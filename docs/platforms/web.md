## What it is
A signed-in workspace in the browser for the same account the iPhone uses on Doddy's server (`backend/`). Today it shows:
- **Documents** Doddy made from the phone: decks, Word, Excel, PDF, text. Their status is real, and they can be downloaded. The server keeps them 7 days.
- **Connected apps**, read-only.
- **Activity:** the server's receipts.
- **Signed-in browsers**, each with Sign out.
- A **language** switch: Polish by default, or English.
- **Logbook** (ADR-602, `docs/product/WEB_LOGBOOK.md`): how a person uses Doddy, in two tabs, At a glance (the week as a receipt) and Closer look (7, 30, 90 days or a year; kept 1 year). The server keeps and serves the days the iPhone sends (`backend/src/web/logbook.ts`, `/v1/web/logbook*`). Since 9 Nov the iPhone sends them, **on by default** (decision `2026-11-09-usage-counts-on-by-default`), and `IPHONE_SENDS_LOGBOOK` is true. `LOGBOOK_ENABLED` in `web/src/logbook/config.ts` hides the page.
- **Admin dashboard** (`/admin`, decision `2026-11-09-usage-counts-on-by-default`): the owner's own dashboard, outside the workspace menu and shell, in its own code chunk (fetched only when `/admin` is opened). Only the accounts in `DODDY_OWNER_ACCOUNTS` get data: for everyone else the server says "not found" and the page sends them to Home; an owner sees an "Admin" link in the menu. Counts only: no word anyone said exists in any number shown.
  - **Five sections:** Overview (accounts, active today, in 7 and 30 days, activation, trouble; accounts per day with new accounts; a "Needs attention" list computed from the numbers; the activity funnel; the most used tools), Users (every account with email, sign-in, last use, a 14-day sparkline and its state; search, filters, sort; a drawer with that account's own days and tools), Tools (every tool as a bar by result, "Said no" kept apart from "Didn't work"), Conversations (weekday-by-hour heatmap, lengths, how they end, languages, tasks), Growth (tasks that worked out each week, new accounts, sign-in methods, activation, weekly retention cohorts with value in week 4, and cohorts from each account's first task that worked out). Every chart has a table twin and a keyboard-reachable tooltip; the period is 7, 30, 90 or 365 days.
  - **Where the data comes from:** Logbook days (`backend/src/web/owner.ts`, `/v1/web/owner*`); emails, names, sign-in methods and join dates from Supabase's admin API with `SUPABASE_SECRET_KEY` (read once a minute). Without the key the dashboard says so and shows Logbook's counts only; cohorts and activation need the join dates. **Not run against the live Supabase**: the account list is tested against a stand-in.
  - **Tasks that worked out (decision `2026-11-14-tasks-that-worked-out`):** Growth's first card. A task that worked out is a tool result Logbook counts as `done`, less the ones `undone`; Logbook's `done` also holds look-ups, opened apps and cards shown for the person to act on (`LogbookBuilder.swift`), so the card says it is not only changes Doddy confirmed. For each of the last 8 weeks (Monday to Sunday, the current one so far): accounts that used Doddy, tasks that worked out, per account to one decimal, the share of accounts with at least one, and the guardrails beside it (not sure and didn't work as shares of the tries that ran, undone of the done ones, said no of everything asked). The weekly cohorts gain **value in week 4**: of the accounts whose days 22 to 28 after joining are over, the share with a task that worked out on one of them (an account whose window hasn't closed counts in neither number). A second cohort table starts from each account's **first task that worked out**, found as far back as Logbook keeps (365 days); it needs no account list. The overview now reads every kept Logbook day (it read 8 weeks before), the same range the account list already reads. Tested in `backend/test/owner.test.ts`, `web/test/adminLogic.test.ts`, `web/test/adminPage.test.tsx`; **not tried on the live site**.
  - **Who can open it, and the record (decision `2026-11-14-owner-panel-fresh-sign-in`):** a browser only: the iPhone's own session gets 401 on every `/v1/web/owner*` route, owner or not. The three routes that show data (`overview`, `accounts`, `accounts/:id/logbook`) answer only within **15 minutes of that browser signing in** (`OWNER_FRESH_MS`, the same window as deleting the account from a browser); later they answer 422 `refused` and show nothing, and the page says to sign out and sign in again (Apple, Google or a code). `GET /v1/web/owner`, which only decides whether the menu shows "Admin", holds no data and has no time limit. Each use that shows data first writes one row to the `owner_audit` table (when, the owner's account id, the browser session id, which of the three it was, and for one account's Logbook that account's id): no email, name, count, word or credential, and if the row can't be written nothing is shown. Rows are pruned after 365 days (`OWNER_AUDIT_KEPT_DAYS`). A refused request writes nothing. There is no screen for it: read it in the database, e.g. `SELECT to_timestamp(at / 1000), actor_id, action, target_id FROM doddy_backend.owner_audit ORDER BY id DESC LIMIT 50`. Run in tests only (`backend/test/owner.test.ts`, `web/test/adminPage.test.tsx`); **not tried against the live site**.
  - **Code and tests:** `web/src/pages/AdminPage.tsx`, `web/src/admin/` (`logic.ts` is the rules with no screen; `charts.tsx` the hand-built SVG charts), `web/src/styles/admin.css`; `web/test/adminPage.test.tsx`, `adminLogic.test.ts`; backend `test/owner.test.ts`. Fixtures come from `npm run fixtures:owner` in `backend/`.
- **Memory** (ADR-603, `docs/product/CLOUD_MEMORY.md`): the notes and conversations a person chose to keep on Doddy's server, as text, kept for a year, encrypted with a server-held key; read, searched, downloaded and deleted from the browser, and the chat (below), where Claude (`DODDY_CHAT_MODEL`, default `claude-haiku-5-5`) answers from them and cites its sources. **The iPhone's sending is written and compiles in the hosted Mac job, but hasn't run on a device**, so the page opens on "nothing is kept" and is marked Soon in the menu (`IPHONE_SYNCS_MEMORY` in `web/src/memory/config.ts`). The server needs `DODDY_MEMORY_KEY`, or it says "not set up".

- **Chat** (ADR-657, numbered 604 on its branch; `docs/product/WEB_CHAT.md`): `/chat`, laid out like ChatGPT in Doddy's colours (the list of chats, the conversation, a round message box, suggested questions, sources under each answer, "What I can see"). It replaces Ask Doddy (`/ask` opens it). Claude answers from the kept notes and conversations **and the account**: Logbook's counts added up per period, counts over kept conversations, connected apps, the documents Doddy made and his receipts, all as cited data. So it already answers about apps, documents and activity, and about usage counts now that the iPhone sends them; notes and conversations follow when the iPhone sends them. The list of chats is kept **in this tab only** (`sessionStorage`): a reload keeps it, closing the tab forgets it, and Sign out deletes it (decision `2026-11-14-owner-panel-fresh-sign-in`; before that it was `localStorage`, which survives closing the browser, so what an older version left there is moved into the tab for the same sign-in and deleted otherwise, as soon as the page knows who is signed in). Tested with the demo model only. **Live on Render since 24 Oct 11:08 UTC** (first `69762f6`, now `main`'s `360c99f`; signed-in use with the real model not checked yet).

- **Messages** (`docs/implementation/MESSAGES_WEB_SYNC.md`, `web/src/pages/MessagesPage.tsx`): a read-only copy of the iPhone's Messages thread, which the iPhone sends encrypted and without photos to `PUT /v1/web/messages` (table `message_threads`, needs `DODDY_MEMORY_KEY`). The menu says Soon (`IPHONE_SENDS_MESSAGES = false`) until an iPhone build that sends it is installed.

It does not have tasks or projects. Home says so instead of showing empty versions of them.

Doddy Web follows the website's design (owner, 22 Oct): the cream canvas, a sticky header with the wordmark, the sections in one row and Sign out (a Menu sheet on small screens), paper cards with a soft lift, ink buttons with the orange underline, ruled notebook panels for Home and sign-in, Doddy's handwritten line. Dark mode stays (the website is light-only), using the same palette file's dark values.
- **Colours** come from `CandidateTokens.swift`, the file the website's `tools/gen_site_tokens.py` reads, through `tools/gen_web_assets.py`. Before 22 Oct they came from `UploadedTokens.swift` (orange `#EC803F`); the website's orange is `#FF6A00`.
- **Fonts:** the website uses Bricolage Grotesque and Caveat from Google Fonts. Matching the website exactly is an owner decision (`WEB_LOGBOOK.md`, decision 2).
- **Poses:** Doddy's poses are the app's `WholeDoddy_*` images, copied by `gen_web_assets.py` (`crosslegged`, `belly_reading`, `shush`, `wave`, `kneeling_inspect`).

## How signing in works (ADR-600)
1. On the iPhone: Settings › Doddy on the web › Get a sign-in code. The phone shows eight letters and digits and the web address to type them at.
2. In the browser, at that address: type the code. It works once, for five minutes.
3. The browser gets an HttpOnly, SameSite=Strict cookie for the same server account. It lasts 30 days, or until 14 days unused.

The phone can list and sign out every browser. A browser can sign itself or others out.

Limits on typing codes (`REDEEM_LIMITS`, `src/web/sessions.ts`): 10 tries per client address (an IPv6 /64) per quarter hour, right or wrong, counted before the code is read. For the whole server only **wrong** codes count, 2,000 an hour. While that hour's budget is spent, a client's first try of the quarter hour is still checked, so a right code still signs in; only a client that already had a wrong code this quarter hour gets 429 until the quarter hour ends. Wrong codes from many places can't lock everyone out.

## Google and Apple (ADR-818, `2026-11-09-web-sign-in-same-account`)
The code still works. Next to it, the sign-in page shows "Continue with Google" and "Continue with Apple" once the server has `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`; `DODDY_WEB_SIGNIN_PROVIDERS` (default `google,apple`) picks which buttons. They open the Doddy account the iPhone uses for that same Apple or Google sign-in (decision `2026-11-09-web-sign-in-same-account`: the Supabase user's own id, or the id of the iPhone's earlier data it took over), with nothing to link. A *different* Apple or Google user (say Google on the site, Apple on the iPhone) opens an account only after it is linked to it once:
- **On the iPhone:** Settings › Doddy on the web › Link Google (or Apple). The phone opens the system sign-in sheet with a one-time ticket from the server.
- **In a browser signed in with a code:** Settings › Sign-in methods › Link.

Linking from the iPhone takes effect only when that iPhone confirms it with its own session, so a ticket forwarded to someone else can't link their account to the sender's. A browser can link or unlink only within 15 minutes of signing in with a code. A Google or Apple account that isn't linked to any Doddy account can make a new one (owner, 3 Nov 2026): the sign-in page asks "Make a Doddy account with Google?", and only "Create my Doddy account" makes it (`POST /v1/web/signup`); `DODDY_WEB_SIGNUP=off` stops that. The new account has the Supabase user's own id, so an iPhone that uses the same sign-in is in the same account. A web-made account starts empty (unless the iPhone already uses that sign-in), works with the web workspace and the chat, and is deleted in Settings › Delete account (an iPhone's account is still deleted on the iPhone). The iPhone app can sign in to it too: Settings › Doddy on the web › Your account from the web › Sign in with Google (ADR-819). One that is linked to another Doddy account is refused, and nothing is merged. Both sides list and unlink. The server runs the sign-in itself (OAuth with PKCE through Supabase Auth, `backend/src/web/social.ts`), so the browser never holds a Supabase token. The owner's setup steps (Google and Apple in Supabase, the redirect address, Render's two variables) are in `docs/integrations/DEPLOY_RENDER.md`, "Google and Apple on the web". **Not tried against the real Supabase, Google or Apple, and no device run of the iPhone part is recorded.**


**In a small window (10 Nov 2026, `web/src/auth/popup.ts`).** On a wide screen with a mouse, "Continue with Apple or Google" opens the server's start address in a small window and the sign-in page stays; it asks the server (`GET /v1/web/session`) every 1.5 s, on focus and when the window says it finished (BroadcastChannel), and opens Doddy itself once the session cookie, set in the window, exists. The server and the sign-in rules are unchanged, and nothing the window says is trusted. A phone or narrow screen, a ctrl/shift/middle click and a blocked window keep the whole-page redirect. If the server's answer is a result (`new_account`, `not_linked`, `canceled`, `failed`, `busy`), the window hands it to the page and closes, and the page shows it as before. The page waits at most five minutes and has a Cancel button. Tested in jsdom and once in Chromium against a stand-in server; **not** with the real Apple, Google or Supabase pages.

## Doddy accounts on the server (decision `2026-11-08-required-account`)
Every user is getting a Doddy account: a Supabase user made with Apple, Google or a code sent by email. The iPhone talks to Supabase itself; this server only checks the token (ADR-526, `DODDY_AUTH_MODE=supabase`).
- **Email counts now.** The token check accepts `apple`, `google` and `email`. It refuses any session whose `amr` names a password (`madeWithPassword`, `src/auth.ts`), even if password sign-in were left on in the project.
- **Linking an iPhone's earlier data** takes two steps, so the iPhone itself takes part each time (a device token alone links nothing):
  1. `POST /v1/account/link-device/start`, with the iPhone's own device token (`ds1`) in the Authorization header and no body. Answers `{ "linkCode", "expiresAt" }`: a one-time code that works for five minutes and is kept only as a hash (`account_link_codes`). A newer code replaces an older one. A guest's token (`scp: "ask"`) gets 403 `permission_insufficient`: it keeps no data. An invalid, expired or cut-off token gets 401.
  2. `POST /v1/account/link-device`, with the account in the Authorization header and `{ "linkCode": "…" }` in the body. Answers `{ "linked": true }`. A used, expired or unknown code: 400 `attempt_invalid` (the iPhone asks for a new one). The one-step body `{ "deviceToken" }` of the first version is refused with 400 `invalid_request`; an app from before this answer reads it as "try later" and keeps its device session.
  - The link writes one row of `account_links`, mapping the account to the device's user id. From then on the account works on that data, and the device token is refused, so `POST /v1/session/device` for that iPhone answers 409 `account_conflict`.
  - A repeat (both steps again, a new code) answers the same way, so the iPhone can safely try again after a lost answer.
  - Accounts are never merged, so the route refuses with 409 `account_conflict` when the account already has data of its own, when it already took over another iPhone's data, or when another account took over this iPhone's data. The code is used up either way.
  - **Undo, for a day:** `POST /v1/account/link-device/undo` with the iPhone's device token (still accepted here after the link) and no body. Within 24 hours of the link it removes the link, revokes browser sessions opened for that data since the link, and removes Apple or Google sign-ins linked to it, iPhones that joined it and unused sign-in codes or tickets made since then. Answers `{ "linked": false }` (also when nothing was linked). Later: 409 `account_conflict`. Data written meanwhile stays with the iPhone's data. DoddyCore has the call (`undoBackendLink`); no screen offers it yet.
  - **Operator unlink**, any time: `DATABASE_URL=… npm run account:unlink -- <account-or-data-user-id>` in `backend/` (`src/unlinkAccount.ts`, `Store.unlinkAccount`), the same clean-up as the undo.
  - Limits: 10 link tries per account per hour, and 10 codes or undo tries per iPhone per hour. Without a Supabase project all three routes answer 503 `live_not_configured`.
  - Code: `src/accountLinks.ts`, `Store.linkAccountWithCode`, `Store.undoAccountLink`.
- **Deleting the account** (`DELETE /v1/account` with the account's token):
  - erases the linked data;
  - queues the Supabase user for removal (`supabase_auth` cleanup; it needs `SUPABASE_SECRET_KEY`, as for ADR-818);
  - ends that account's earlier tokens at once, through its cut-off second;
  - refuses, with 401 like a cut-off token, a write by a request that was let in before the deletion and was still running when it committed (the `users` row, receipts, switches, documents, payments, approvals). The cut-off row in `token_floor` is the deletion's tombstone, kept 31 days; the check runs in each write's own transaction (`Store.refuseIfCutOff`, `src/requestCredential.ts`). A sign-in made after the deletion writes as usual.
- **Removals still owed after a deletion** (an online account's connection, a Supabase user) are never given up: the hourly sweeps retry each one, waiting longer after each failure (5 minutes, doubling, at most a day; `CLEANUP_RETRY`, `src/store.ts`). After 8 failures, or at once when the server has no way to remove that kind (`supabase_auth` without `SUPABASE_SECRET_KEY`), it is reported stuck: one `cleanup_stuck` warning in the log (kind, tries, reason; never an id) and `stuck_at` on the row. `DATABASE_URL=… npm run cleanups:stuck` in `backend/` lists them, with the provider's id to remove by hand.
- **Tests:** `backend/test/account-links.test.ts` builds the real app from its config (supabase mode, device sign-in on, a local ES256 key in place of the project's). `auth-supabase.test.ts` covers email and passwords.
- **To turn it on, live:** `DODDY_AUTH_MODE=supabase` and `SUPABASE_URL` on Render `doddy`. Keep `DODDY_SESSION_SIGNING_KEY` while phones move over: old device tokens, the link's first step and the undo need it. Deploy the server before an app build with the two-step link: an app with it gets 404 from an older server and tries again later. Render runs `DODDY_ENV=development`, where that is allowed.

## Deploy
The web app is served by the existing Render service `doddy`, so there's no new host and no new monthly cost. **This has been done** (live since 22 Oct, see State); the steps below are for a rebuild or a new service. Whether `DODDY_WEB_ORIGIN` is `https://app.doddy.lol` or the Render address isn't recorded here.
1. **Build command** of the hand-made Render service `doddy` (Settings › Build & Deploy): `npm ci --ignore-scripts && npm run build && npm ci --prefix ../web && npm run build --prefix ../web`. The same line is in `render.yaml`. The server's install skips package scripts because none of its locked packages has one; the web install keeps them, because its build tool (esbuild) has an install script. Render runs it in `backend/` (the root directory). That the rest of the repository is checked out next to it is expected, but unverified; if not, set the root directory to the repository and prefix the backend commands with `--prefix backend`.
2. **Environment** of `doddy`:
   - `DODDY_WEB_ORIGIN=https://app.doddy.lol`, once that name points at the service as a Render custom domain (owner decision 8). This is recommended: the phone's signed document links stay on `DODDY_PUBLIC_BASE_URL` (the Render address), a different origin from the web session. `https://doddy-yaci.onrender.com` also works for a first try; then those links share the web app's origin (see the audit's security section).
   - `DODDY_TRUST_PROXY=1`.
   - Optional: `DODDY_WEB_SIGNIN_TRIES_PER_CLIENT` (default 10 per quarter hour; raise it for an office behind one address).
   - Signing in with a code and the pages add nothing secret (Google and Apple sign-in need `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`, above). `DODDY_SESSION_SIGNING_KEY` and the database are already there.
   - The admin dashboard needs `DODDY_OWNER_ACCOUNTS` (the owner's account ids, comma-separated); `SUPABASE_SECRET_KEY` adds emails, names and join dates (and deletes a person's sign-in, ADR-818). Without the first there is no dashboard.
   - Memory and Messages need one secret, `DODDY_MEMORY_KEY` (base64 of 32 random bytes); without it they say "not set up". It isn't in `render.yaml` or `secrets/manifest.json` (the 7 Nov audit asks for it).
3. **Deploy** the branch or main (autoDeploy is off). Check:
   - `GET /v1/health` answers `{"status":"ok"}` (status only; the start log's `listening` line names the mode and the running commit);
   - `GET /` shows the sign-in page, not "isn't built";
   - the response headers include `content-security-policy`.
4. **Phone:** a build with this branch (the hosted Mac CI is its first compile), then Settings › Doddy on the web › Get a sign-in code, and sign in from a computer.

**Rollback:** unset `DODDY_WEB_ORIGIN` and redeploy. The web routes and pages disappear (404), and the phone's API is untouched. Browser sessions stay in the `web_sessions` table until pruned. To end them at once:
```sql
UPDATE doddy_backend.web_sessions SET revoked_at = (extract(epoch from now()) * 1000)::bigint WHERE revoked_at IS NULL;
```
