### [1] Sign-out leaves messaging credentials and private push delivery active

| Field | Value |
| --- | --- |
| Severity | medium |
| Confidence | high |
| Confidence rationale | Direct source traces local-only logout, unexpired server bearer lookup and continued push selection; no live phone or stolen-token test was performed. |
| Category | Insufficient session expiration |
| CWE | CWE-613 |
| Affected lines | DoddyApp/Features/Account/DoddyAccountApp.swift:270-273, server/messaging/src/auth.ts:20-31, server/messaging/src/outbox.ts:243-255 |

#### Summary

Sign in, register push notifications, then sign out. The app removes its local credentials, but the messaging server device row remains authorized and its APNs binding remains usable. A previously copied messaging token can still access that account, and later private notification bodies can reach the signed-out phone. This does not establish a way to steal or guess a token.

#### Root Cause

Local credential deletion is treated as full logout although messaging maintains independent server-side device authority and APNs state.

#### Severity

**Medium** — Access requires an already captured valid token, or access to the previously registered phone. Strong random hashed tokens, account erasure, and APNs rebinding limit exposure, but sign-out does not terminate authority or private notification delivery.

Confirmed deployment-level token expiry or revocation would lower severity; a demonstrated token extraction path would raise it.

#### Remediation

- Verify other devices remain authorized when only one device signs out.

Preventive controls:
- Treat all independently issued credentials as part of a single account lifecycle.
- Use privacy-preserving notification previews.

### [2] A late token refresh can restore the account after sign-out

| Field | Value |
| --- | --- |
| Severity | medium |
| Confidence | medium |
| Confidence rationale | The unguarded asynchronous state mutation is directly visible; actual overlap and user-facing effects still require deterministic transport tests. |
| Category | Authentication state race |
| CWE | CWE-362 |
| Affected lines | Packages/DoddyCore/Sources/DoddyCore/Account/DoddyAccountModel.swift:203-212, Packages/DoddyCore/Sources/DoddyCore/Account/DoddyAccountModel.swift:183-187, Packages/DoddyCore/Sources/DoddyCore/Account/DoddyAccountModel.swift:219-237 |

#### Summary

Start an account refresh, sign out while it is pending, then let the refresh succeed. The resumed refresh unconditionally saves and reinstalls its previous account session. A refresh from account A can similarly overwrite account B after a switch; a late signed-out error can clear the newer session.

#### Root Cause

Asynchronous account results retain authority to write session state after the account lifecycle has moved on. MainActor serialization does not prevent reentrancy across await.

**Logout does not invalidate pending refresh** — `Packages/DoddyCore/Sources/DoddyCore/Account/DoddyAccountModel.swift:184-187`

The logout path forgets the account but neither increments an auth generation nor prevents a pending task from installing old credentials.

```swift
    public func signOut() async {
        if let session, let client { await client.signOut(session) }
        forget(message: nil)
    }
```

**Suspended refresh installs results without an identity generation check** — `Packages/DoddyCore/Sources/DoddyCore/Account/DoddyAccountModel.swift:202-212`

Main actor execution can resume after logout or a new sign-in; success and failure mutate the current state without verifying that this refresh still owns it.

```swift
        refreshing = task
        let result = await task.value
        refreshing = nil
        switch result {
        case .success(let fresh):
            guard store.save(fresh) else { throw .unavailable }
            session = fresh
            return fresh
        case .failure(.signedOut):
            forget(message: DoddyAccountError.signedOut.userMessage)
            throw .signedOut
```

#### Reachability

Requires an in-flight refresh overlapping logout or account adoption. Relevant to shared-device privacy and session integrity; not evidence of an unauthenticated remote attack.

#### Severity

**Medium** — A timing-dependent account lifecycle failure can defeat the expected signed-out state or replace the active identity on a shared phone. It requires overlapping authentication operations; no anonymous remote trigger or reliable physical-device exploit was demonstrated.

A deterministic device reproduction involving private data would strengthen impact; an enforced unreachable concurrent UI path would lower exploitability.

#### Remediation

Invalidate an authentication generation on logout and every new account adoption. Capture the generation and subject before refresh, and check both before applying success or failure. Cancel old work as a best effort, but rely on the generation check for correctness. Ensure server credential synchronization obeys the same account boundary.

Tests:
- Delay refresh completion until after logout; late success must leave storage and session empty.
- Delay A refresh until B signs in; neither late success nor failure may overwrite or clear B.
- Verify concurrent refresh callers cannot receive usable old-account credentials after generation changes.

Preventive controls:
- Make asynchronous account writes conditional on current principal and generation.

### [3] Generated provider files can survive local cleanup and account erasure

| Field | Value |
| --- | --- |
| Severity | low |
| Confidence | high |
| Confidence rationale | Source directly shows in-memory references, exceptions before cleanup, and unchecked DELETE responses; actual provider retention was not tested. |
| Category | Incomplete sensitive resource cleanup |
| CWE | CWE-459 |
| Affected lines | backend/src/tools/claude.ts:264-265, backend/src/tools/claude.ts:321-322, backend/src/tools/claude.ts:237-249, backend/src/store.ts:943-979 |

#### Summary

Generate a document and interrupt processing after remote file IDs are received, or let the provider reject a cleanup request. File IDs exist only in memory, cleanup is fire-and-forget, and HTTP deletion failures are ignored. Remote copies can remain without an account-linked retry record.

#### Root Cause

External file retention obligations are not durable account-owned resources; successful generation dispatches unverified deletion rather than recording a retryable completion.

**Cleanup is only attempted on successful download** — `backend/src/tools/claude.ts:263-265`

Download errors skip this cleanup and process termination loses its in-memory obligations.

```typescript
    const bytes = await this.fileContent(chosen.id, signal);
    // Best effort: Doddy keeps its own copy for a week; Anthropic's copy isn't needed.
    for (const id of fileIds) void this.deleteFile(id).catch(() => {});
```

**Provider deletion response is not checked** — `backend/src/tools/claude.ts:321-323`

HTTP failure statuses resolve fetch normally and are accepted as successful cleanup.


#### Reachability

Ordinary generation plus provider/network/process failure is sufficient for retention. This finding does not assert that another app user can retrieve those files.

#### Severity

**Low** — This is a privacy and retention failure for provider-hosted document copies. The repository does not establish public accessibility, an ordinary attacker read path, or the provider retention duration.

Evidence that orphaned files are publicly accessible or retrievable across tenants would raise severity; verified provider automatic deletion would narrow the risk.

#### Remediation

Persist provider file IDs with account ownership as soon as observed. Use finally cleanup, validate deletion success or not-found, and retain a durable retry queue through account erasure until deletion is confirmed. Apply this pattern consistently across generation providers.

Tests:
- Force timeout after file creation; cleanup obligation must survive restart.
- Return 429/500 from DELETE; retain and retry the cleanup job.
- Erase an account while cleanup is pending; preserve cleanup references until confirmed deletion.

Preventive controls:
- Track external personal-data copies in an account-owned resource inventory.
- Monitor cleanup failures and retention age without logging document contents.
